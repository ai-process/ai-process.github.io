One switchboard for every LLM you run

Keystone. The Model Switchboard. (KTMS) is a self-hosted LLM gateway: it keeps your vendor keys, routes each request by effort, falls back when a provider fails and caps spend. light-tokenmeter shows who burns the tokens. ktms-admin puts it all in your browser.

Products

Three small services. One production stack.

Use them together or one at a time. Each is a single Go binary with its own Docker image, Helm-friendly defaults and an Apache 2.0 licence.

Keystone. The Model Switchboard. (KTMS)

LLM gateway · gRPC & HTTP

Your services talk to one endpoint. Keystone holds the vendor keys, picks the model, retries elsewhere when a vendor is down and records every call.

  • Vendor keys encrypted in Postgres (AES-256-GCM): OpenAI, Anthropic, Gemini, DeepSeek
  • Routing rules by effort and attributes, changed live
  • RPM, daily token budgets and USD spend caps per key, user and team
  • Batches at 50% off, speech, images, typed Judge
  • Pool of your own GPU nodes with cloud fallback
Docs → GitHub Docker Hub

light-tokenmeter

Usage meter · Postgres / ClickHouse

Your apps, or KTMS, push one event per model call. Ask who is spending your tokens, and whether they are worth it.

  • Append-only, idempotent events: sending twice is harmless
  • Bearer tokens with write and read scopes, Prometheus metrics
  • Daily summaries with any filters and groupings
  • HTTP/JSON for dashboards, gRPC for services
  • Optional ClickHouse for large volumes, with no lost events
Docs → GitHub Docker Hub

ktms-admin

Web console · one static binary

Manage models, routing rules and keys, try a prompt in the playground and read the spend dashboard. No more grpcurl.

  • Password, OpenID Connect, GitHub or access-proxy sign-in, read-only users
  • Greedy / worthy verdict per project, user and model
  • Works with Keystone, light-tokenmeter or both
  • UI embedded in the Go binary, no front-end build
  • Light and dark themes, usable from a phone
Docs → GitHub Docker Hub
Why Keystone

Stop hardcoding model names.
Let the gateway decide.

1

Ask for effort, not for a model

Clients send effort: LOW | MEDIUM | HIGH and free-form attributes. An ordered rule list maps them to a chain of models with fallbacks.

Rules change at runtime over the admin API or in ktms-admin. A new model release is a config change, not a refactor across a dozen services.

2

Your GPUs first, the cloud when they are busy

Run Ollama, vLLM or llama.cpp on your own hardware. ktms-node-agent registers each machine and reports VRAM, time to first token and tokens per second.

KTMS balances the pool with Smooth WRR, keeps hot or overloaded nodes out of rotation and, with nodes_first, spills over to cloud vendors only when local capacity runs out.

3

Budgets that actually stop the spend

Per-model requests-per-minute and daily token budgets for every API key and every end user, plus hard USD spend caps per key, user and team, enforced in Redis before the vendor ever sees the request.

Non-interactive work goes through the vendors' Batch APIs at a 50% discount, with background polling and a synchronous fallback.

Know who is greedy and who is worthy

KTMS sends one usage event per call to light-tokenmeter. Slice spend by project, user, action, vendor or model, with failure rates and latency next to the cost.

ktms-admin turns it into a verdict: the workloads that burn tokens for little value, and the ones that earn them.

Quick start

From git clone to a routed request

Start the stack

Docker Compose brings up KTMS with Postgres and Redis, seeds default models and rules and a dev key.

Point your SDK at it

Change base_url and use model: "auto". Routing, fallbacks and limits come for free.

Go to production

Docker images for amd64 and arm64, a Helm chart and a production checklist are in the KTMS docs.

git clone https://github.com/ai-process/ktms.git
cd ktms

# any of OPENAI_API_KEY, GEMINI_API_KEY, ANTHROPIC_API_KEY
OPENAI_API_KEY=sk-... docker compose up -d --build

curl -s http://localhost:8080/readyz   # {"status":"ready"}
curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer ktms_dev_default_key" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"Say hi in three words."}]}'

# response headers tell you who answered and why:
# X-KTMS-Vendor, X-KTMS-Rule, X-KTMS-Placement
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1", api_key="ktms_dev_default_key")
response = client.chat.completions.create(
    model="auto",  # or "auto:low", "auto:high"
    messages=[{"role": "user", "content": "Say hi in three words."}],
)
print(response.choices[0].message.content)
